# Research: pipelines as PMTiles, and a DuckDB query console

Research note for R4 (post-launch candidates list in CLAUDE.md: "pipelines as PMTiles, query console"). No code changed. Measurements taken 2026-09-19 against the current `main` tree.

## Part A — Pipelines as PMTiles

### The status quo, measured

`public/data/pipelines.geojson` is 8,110,806 bytes (7.9 MB) today (post Phase 10 fragment-merge + 6-decimal-place precision fix). Compressed as Vercel would serve it:

| Encoding | Bytes | vs raw |
|---|---|---|
| raw | 8,110,806 | — |
| gzip -9 | 1,870,250 | 23% |
| brotli -q11 | 1,255,392 | 15% |

Vercel's edge serves static/`public/` assets brotli-compressed to browsers that send `Accept-Encoding: br` (essentially all of them since 2020), so the real cold-load cost today is **~1.25 MB, once** — `dataUrl()` appends `?v=<sha8>` and `next.config.ts` sends `max-age=31536000, immutable` for versioned URLs (CLAUDE.md, "Versioned data URLs"), so a returning visitor never re-fetches it until the catalog hash changes. This is loaded lazily too: `useMapLayers` only calls `loadPipelines()` when `layers.pipelines || layers.gas_pipelines` is on, and both are on by default in `infrastructure` mode, so most sessions do pay this cost once, but only once per browser per data version.

That is the number a PMTiles migration has to beat, and it has to beat it at **first paint**, since immutable caching already erases the cost on every subsequent load.

### Two implementation paths

**1. deck.gl `MVTLayer` + `pmtiles` package (custom `getTileData`).** deck.gl 9.3.2 (installed: `@deck.gl/core`/`layers`/`mapbox` `^9.3.2`) ships `MVTLayer` (a `TileLayer` specialization that expects Mapbox Vector Tile bytes per z/x/y). It does not natively speak the PMTiles archive format — you subclass it (the documented pattern, e.g. "PMTiles in deck.gl" — Medium/Center for Coastal Climate Resilience Visualization) and override `getTileData` to pull bytes via the `pmtiles` JS library's `PMTiles.getZxy(z, x, y)` and hand them to `MVTLoader.parse`. loaders.gl also ships a `@loaders.gl/pmtiles` module with a `PMTilesSource`, current as of the "What's New" changelog, which is the more idiomatic way to wire this into deck.gl's `TileLayer` data-source API instead of hand-rolling `getTileData`. Either way it's a `Layer` like any other, so it composes into `MapboxOverlay({interleaved: true})` and `anchorBeneathLabels()` unchanged — no MapShell rewrite needed.

- **Tooltips/picking**: `MVTLayer` supports `pickable` + `getTooltip` the same as `GeoJsonLayer`, decoding each tile's features into GeoJSON-shaped `properties`; whatever columns you push into the tile (pipeline_id, name, status, commodity, capacity, operator, start_year) come back at pick time. No change to `formatPipelineTooltip`'s shape.
- **Vintage filter**: this is the awkward part. Today `filterPipelines()` filters in memory per render (`isVisibleAtYear`), which is free because the whole GeoJSON is already in the browser. With tiles, filtering by `start_year` at *render* time either means (a) baking `start_year` into the tile as an attribute and filtering client-side per rendered feature via a deck.gl accessor (`getFilterValue` + `extensions: [new DataFilterExtension()]`) — doable, and it avoids re-fetching tiles per year tick — or (b) tag tiles by decade and swap the URL template (adds moving parts for a 34-year range with only 64-74% start_year coverage and no natural bucket boundary). (a) is the sane choice: deck.gl's `DataFilterExtension` filters already-loaded tile features by a numeric range with zero refetch, so the visible-if-null semantics of `isVisibleAtYear` (treat `null` as `-Infinity`/always-pass) need a sentinel value written into the tile (e.g. `start_year: -1` for null, filter range `[-1, year]`).
- **Symbology (oil/gas/NGL/in-construction)**: `pipelineColor(commodity, status)` becomes a per-feature `getLineColor` accessor same as today, reading `commodity`/`status` off tile properties — same code, different data source. No change to `src/lib/symbology`.
- **Z-order under labels**: unaffected — still a deck.gl `Layer`, still gets `beforeId` from `anchorBeneathLabels()`.
- **Scenario highlighting of specific pipeline_ids**: works the same way (`updateTriggers` keyed on the impacts map), but only for features present in whichever tiles are currently loaded at the current viewport/zoom — a highlighted pipeline scrolled off-screen or in an unloaded tile won't recolor until its tile loads. Today's single in-memory GeoJSON has no such gap.
- **e2e pixel probes**: `tests/e2e/network.spec.ts`-style specs that wait on `data-ready` and click through helpers would need to wait on tile-load completion instead of a single fetch resolving — `MVTLayer` exposes `onTileLoad`/`onViewportLoad`-style hooks, but there's no single "the data is in" boolean the way a `useAsync` promise gives you today. This is a real testability regression versus the current "one fetch, one loading state" architecture that `useMapLayers`/`useAsync` is built around project-wide (CLAUDE.md: "One data path").
- **Cold-load bytes at world view**: at the default view (whole world, low zoom), a well-built tile pyramid actually **not** cheaper than 1.25 MB brotli — at world zoom you need the union of all tiles covering the visible area at the current zoom level, and low-zoom tiles for a *line* dataset (not sparse points) carry nearly all the geometry because pipelines exist everywhere at once; tiling mostly helps when the user is zoomed into one region and doesn't need the rest of the world's pipelines. A world-view first paint would fetch most of zoom-2..4's tiles, which is not much smaller than the current single fetch, and each tile is a separate HTTP request (mitigated by HTTP/2 multiplexing but not free — dozens of small requests vs. one, each with router/edge overhead).
- **Tile-boundary artefacts on long merged lines**: MVT tiling clips lines to tile bounds and re-stitches at render time by drawing per-tile clipped segments; this is normally invisible for filled polygons but for **thin lines styled with joins/caps** (pipelines are 1.25px hairlines here) you can get visible seams or duplicate/missing endpoint caps at tile boundaries, worse at oblique angles crossing a tile edge — a bug class do not currently have.

**2. Native MapLibre vector source + `line-layer` via the `pmtiles://` protocol.** MapLibre GL JS (`maplibre-gl ^5.24.0`, already installed for the basemap) has first-class PMTiles protocol support (`maplibregl.addProtocol("pmtiles", ...)` from the `pmtiles` package) and a native `line-layer` type purpose-built for exactly this. This is the more idiomatic and almost certainly the *cheaper-to-build and cheaper-to-run* of the two paths, since MapLibre's vector tile renderer is written for this in C++/WebGL directly, not reimplemented in a deck.gl tile layer.

- **Tooltips/picking**: MapLibre's `queryRenderedFeatures` at the pointer gives you feature properties on `mousemove`/`click`, same shape. But **this breaks the project's "one canvas" architecture** (CLAUDE.md: "There is one canvas (`.maplibregl-canvas`)... MapLibre owns the canvas and the camera; deck.gl renders into MapLibre's WebGL2 context"). Picking would now be split between deck.gl's `pickingRadius`/`getTooltip` (for every other layer) and MapLibre's own hit-testing (for pipelines only) — two different tooltip code paths, two different pick APIs, and `page.tsx`'s per-layer-id tooltip dispatch (`formatXTooltip`) would need a second dispatch mechanism live entirely outside deck.gl.
- **Vintage filter**: MapLibre supports data-driven `filter` expressions natively (`["any", ["!", ["has", "start_year"]], ["<=", ["get", "start_year"], ["literal", year]]]`), which is actually a cleaner fit for the null-means-always-visible semantics than deck.gl's `DataFilterExtension` sentinel hack above, and it's a plain style-spec filter update on year change (no relayout).
- **Symbology**: MapLibre `line-color`/`line-width` data expressions can replicate `pipelineColor`, but now symbology logic is duplicated in two languages — TS functions in `src/lib/symbology/` for every other layer, and MapLibre style-expression JSON for this one. The CLAUDE.md invariant "No inline RGBA in layer files... Legend renders from the same constants" would need either (a) a code generator translating `pipelineColor`'s cases into a style expression at build/runtime, or (b) accepting genuine logic duplication and drift risk.
- **Z-order under labels**: straightforward and arguably more correct — it's a real MapLibre layer, so `map.addLayer(pipelineLayer, firstSymbolLayerId)` is the exact primitive `firstSymbolLayerId()` already computes for deck's `beforeId`.
- **Scenario highlighting**: same `filter`/`paint` expression update per pipeline_id set — fine for a handful of ids, unwieldy for scenarios that touch hundreds (very long `["in", ["get","pipeline_id"], ["literal",[...]]]` expressions are supported but not elegant, and Hormuz/Druzhba/BTC/CPC scenarios only touch tens of pipelines, so this is a non-issue in practice).
- **e2e pixel probes**: same testability regression as path 1 — no `useAsync`-shaped "loaded" boolean; you'd wait on MapLibre's `idle` or `sourcedata` events with `isSourceLoaded()`, a different signal than every other spec.

**Verdict on the two paths**: if this is ever done, path 2 (native MapLibre vector source) is the right one — deck.gl's `MVTLayer` is really built for point/polygon choropleth-style large data (its own docs example is US Census tracts), not for a hand-styled network that already has bespoke per-status/per-commodity color logic living in `src/lib/symbology`. But path 2 requires accepting a second, non-deck.gl picking and styling system for exactly one layer, which cuts against three separate CLAUDE.md invariants at once (one canvas / one data path / symbology lives in one module) for a layer that is 7.9 MB raw and 1.25 MB compressed-once today.

### Building the tiles reproducibly

`tippecanoe` is confirmed not installed and cannot be installed here (no brew). Checked concretely:

- **`pmtiles` Python package**: as of PMTiles v3 (Protomaps blog, "What's new in PMTiles V3"), the Python CLI tooling for *creating* tiles was **deprecated** — the current Python package is a reader/index library (for serving ranges from S3/GCS/disk), not a tile generator. Not a route to building tiles.
- **GDAL's native PMTiles driver (confirmed working here, no brew/docker)**: `pyogrio` — already an indirect dependency of `geopandas`, which `scripts/transform/build_pipelines.py` already imports — bundles GDAL with `PMTiles` and `MVT` among `list_drivers()`. Tested directly against this repo's `uv` environment:

  ```
  $ uv run python -c "from pyogrio import list_drivers; d=list_drivers(); print('PMTiles' in d, 'MVT' in d)"
  True True
  $ uv run python -c "gdf.to_file('test.pmtiles', driver='PMTiles', MINZOOM=0, MAXZOOM=8)"
  # writes a valid, non-empty .pmtiles file, no external binary
  ```

  This is a real, pip-only (no brew, no Docker, no Go binary) route to building PMTiles archives from the same GeoDataFrame `build_pipelines.py` already constructs, using a dependency the project already has.
- **Byte-identical reruns — fails today.** `build_all.py`'s contract is "reruns are byte-identical" (CLAUDE.md; every `build_*.py` is idempotent by design and the catalog's sha256-based cache-busting depends on this — a file that changes bytes with no data change would bust the `?v=` immutable cache for nothing on every rebuild). Tested: writing the same 2,000-feature GeoDataFrame to PMTiles twice in a row produced **different file sizes (2,951,755 vs 2,951,745 bytes) and different sha256 hashes** — almost certainly a timestamp or generation-order artifact GDAL's PMTiles writer embeds (PMTiles' spec header has no mandated timestamp field, but the writer's internal tile-clustering/compression pass is not guaranteed deterministic across runs). This would need to be tracked down and neutralized (e.g., post-process to zero out any non-content bytes, or accept an sha256 that changes even on a no-op rebuild) before it could satisfy `build_all`'s existing idempotency invariant and the data-integrity tests that check for it.
- **Docker/felt/tippecanoe route**: exists (official `tippecanoe` Docker image) but is explicitly out of scope per this task's constraints (no global installs; Docker wasn't ruled out by the prompt but adds a build-environment dependency `scripts/build_all.py` doesn't have today for any other transform — every other step is pure Python/DuckDB).

### Vercel fit

PMTiles archives are read via HTTP range requests (that's the entire point of the format — a client fetches a small directory chunk, then only the byte ranges for the tiles it needs). Vercel's static asset serving supports `Range` requests on `public/` files (the existing DuckDB parquet-extension / Parquet range-read path already depends on this working — `scripts/smoke/run.sh` checks a Range read). The `?v=<sha8>` + immutable-cache scheme from `src/lib/data/urls.ts` would apply to the `.pmtiles` file itself exactly as it does to `pipelines.geojson` today — no scheme change needed once the file is produced.

### Verdict: not worth doing now

The current cost is **1.25 MB, brotli-compressed, fetched once per browser per data version, then cached for a year** — not "8 MB on every load." A PMTiles migration would trade that for: a second picking/styling system outside deck.gl if done the technically-better way (native MapLibre line-layer), a testability regression (no single "data loaded" boolean for e2e), real tile-boundary seam risk on thin hairline pipelines, and a byte-identical-rebuild property that does not hold today and would need real engineering to fix (GDAL's PMTiles writer is not deterministic across runs in a quick, unscientific test here). In exchange, the win is close to zero at the app's actual default view (world), since a linear/network dataset's low-zoom tiles need most of the geometry anyway, and the *only* upper bound that a PMTiles migration reliably beats is the pre-Phase-10-fragment-merge, pre-hyparquet 14 MB (~2.4 MB compressed) file, which is already gone. Revisit only if pipelines grow materially (e.g. coal + AIS layers post-launch push total geometry into tens of MB) or a per-region "zoom in and explore only this basin's pipelines" product need emerges that the current all-at-once GeoJSON genuinely can't serve — neither is true today.

## Part B — Query console at `/query`

### What `src/lib/duckdb/` already provides, and its state

| File | Role |
|---|---|
| `bootstrap.ts` | `getDuckDB()` — caches the *in-flight promise* (not the resolved DB) so concurrent first-load callers share one boot; boots from self-hosted bundles (`bundles.ts`), points the parquet extension at a self-hosted repo when the running core version matches the pinned one, else warns and falls back to DuckDB's default extension repository. `prewarmDuckDB()` kicks the boot off without awaiting it (currently unused — nothing calls it; it predates the hyparquet switch that took DuckDB off the load path entirely). |
| `bundles.ts` | `DUCKDB_CORE_VERSION = "v1.5.1"`, pinned twice (also in `scripts/copy-duckdb.mjs`) with sha256-checked parquet-extension downloads; `selfHostedBundles()` builds `?v=<pkg-version>` URLs under `/duckdb/`. |
| `query.ts` | `query<TRow>(sql, params)` — the actual `read_parquet('/data/<file>.parquet')`-with-hardcoded-paths contract CLAUDE.md documents; registers referenced files with DuckDB by exact logical name before running, normalizes BIGINT→number and DATE→ISO string (`normalize.ts`), returns `{rows, count}`. |
| `files.ts` | Maps a logical `/data/*.parquet` path referenced in SQL to registering it with DuckDB, prefetching bytes in parallel with the WASM boot. |
| `normalize.ts` | Row-shape normalization (BIGINT/DATE) so callers can type columns as `number`/`string` without manual coercion. |

**It still builds and is tested**: `pnpm vitest run tests/unit/duckdb` passes today — 4 files, 24 tests (`bootstrap.test.ts`, `query.test.ts`, `normalize.test.ts`, `files.test.ts`). `scripts/copy-duckdb.mjs` still runs at `predev`/`prebuild` and copies the pinned bundle + downloads the sha256-verified parquet extension. Nothing has bit-rotted; it's simply unreached at runtime (`tests/e2e/network.spec.ts` asserts zero `/duckdb/*` requests on a cold load with every parquet-backed loader active, and passes because nothing on the load path imports `src/lib/duckdb/`).

### Design: `/query`

**Route**: a new `src/app/query/page.tsx`, sibling to `methodology/` and `data/`, linked from the footer/nav (the map footer's *last* link must stay "Methodology" per the a11y focus-order test in `tests/e2e/a11y.spec.ts` — `/query` goes earlier in the footer order, not appended after Methodology).

**Lazy-loading (the network.spec.ts guard)**: the page component must not statically import anything that touches `getDuckDB()`/`bootstrap.ts` at module scope. Two safe patterns already used elsewhere in the codebase's spirit (`useAsync`, dynamic import):
- `next/dynamic` with `ssr: false` for the console's interactive body, so `duckdb-wasm` and the JS glue for `@duckdb/duckdb-wasm` never end up in the `/`  bundle graph or its module-eval order.
- Call `getDuckDB()`/`prewarmDuckDB()` only from an effect scoped to `/query`'s client component, never from anything shared with `page.tsx` (the map route). Because `src/lib/duckdb/` has zero importers today, this is purely additive — no existing import graph to untangle.
- The existing `network.spec.ts` assertion (`gotoReady(page, "/?...")` then `expect(duckdb).toEqual([])`) only visits `/`, so it stays green unmodified; a **new** e2e spec for `/query` should assert the opposite — that visiting `/query` *does* request `/duckdb/*` — as a regression guard in both directions.

**Which Parquet files are exposed as tables — the conservative rule.** LICENSE-DATA.md's existing rule for the `/data` download page is: a file is offered for **download** only when every row's source is CC BY 4.0, public domain, Etalab 2.0, or project-derived (`downloadable: true` in the catalog — 22 catalog entries checked, a mix of `true`/`false`). But the query console is a different act from downloading: running `SELECT` against a table **on-screen only**, with **no export**, is closer to what the app already does for view-only layers — EI reserves, BACI-adjacent view-only tables, GIE daily, UN Comtrade, and `assets.parquet` (which is view-only *only* because of 88 ODbL OSM rows mixed in with everything else, per LICENSE-DATA.md's explicit reasoning) are all rendered on the map and in tooltips today without being downloadable files.

Proposed conservative rule, reasoning from that same distinction the project already draws between "shown in the app" and "offered as a file":
- **Every catalog table (`downloadable: true` or `false`) is queryable on-screen**, because the map itself already displays 100% of every one of these tables' rows in some layer or tooltip — a `SELECT * FROM reserves LIMIT 20` in a console exposes nothing the map doesn't already render. This matches "shown in the app" everywhere else in the licensing doc.
- **CSV/file export from the console follows exactly the `downloadable` flag**, same as `/data` — a query result grid can be viewed and scrolled for any table, but the "Download CSV" button is disabled (with the same `download_note` text already in the catalog, e.g. the ODbL-OSM-rows explanation for `assets.parquet`) whenever the table (or, if the query joins tables, *any* table it reads) is `downloadable: false`. This is the one place this rule is *stricter* than "shown in the app": a `SELECT` that joins a downloadable and a non-downloadable table produces a result that is not simply "the map's rendering" — it is a new derived table, and export of it should not be allowed to bypass the ODbL/ EI/UN Comtrade constraints via a JOIN. Concretely: export is enabled iff `downloadable === true` for every table named in the query's `FROM`/`JOIN` clauses (a static SQL parse, not a runtime row check) — same posture as `assets.parquet` vs `assets_open.parquet` today (offer the open subset as its own table, not gate row-by-row).
- `assets.parquet` itself: since it's already `downloadable: false` for the whole file, treat it as query-only, no export, exactly matching current `/data` behavior; expose `assets_open.parquet` as a second, separately queryable and exportable table (mirrors the existing two-file split, doesn't invent new licensing logic).

**Table naming**: mirror the existing hardcoded-path convention from CLAUDE.md ("Loaders in `src/lib/data/` call `readParquet('/data/<file>.parquet', ...)` directly... hardcode the path in the loader") — register each catalog Parquet file under its filename stem as the DuckDB table name (`assets`, `assets_open`, `country_year_series`, `trade_flow`, `disruption_route`, `lng_voyage`, `lng_trade_daily`, `lng_terminal_daily`, `gie_daily`, `comtrade_monthly`, `shale_region_year`), generated from `catalog.json` at build time (same generator, `build_catalog.py`, already the single source of truth) rather than hand-maintained, so a new dataset added to the catalog appears in the console automatically. GeoJSON sidecars (`pipelines.geojson`, `basins.geojson`, `countries.geojson`) are not naturally SQL tables and are out of scope for v1 — DuckDB's spatial extension was already tried and dropped as unreliable in the pinned dev build (CLAUDE.md), so this isn't new risk, just staying out of a known bad path.

**Example queries**: seed the console's "try one of these" list directly from the worked examples researchers already read — `docs/researchers/worked-examples.md` computes exactly this kind of number ("Central Europe's Druzhba exposure", "who loses most if Hormuz closes") from `trade_flow.parquet` + `disruption_route.parquet` by *reproducing the scenario engine in TypeScript*, not SQL, today. A first console query set should be simpler aggregate queries over the same tables (e.g. `SELECT importer_iso3, SUM(qty) FROM trade_flow WHERE hs_code='2709' AND year=2024 GROUP BY 1 ORDER BY 2 DESC LIMIT 20` — BACI crude imports by country) that a researcher can sanity-check against the worked examples' numbers, not a re-implementation of the scenario engine in SQL (out of scope — the engine's refinery/LNG attribution and route-share pair-overrides logic in `src/lib/scenarios/` is nontrivial and pure-TS by design; duplicating it in SQL for the console would be exactly the kind of drift risk CLAUDE.md's "pure functions for scenarios" convention exists to prevent).

**Result grid + CSV export with citation header**: reuse `src/lib/export/csv.ts`'s `toCsv(columns, rows, comments)` unchanged — it already supports a `# `-prefixed comment header block designed for exactly this ("pandas: `read_csv(path, comment='#')`"). Build the header from the same `Catalog`/citation data `src/lib/export/citation.ts` and `scenario.ts` already expose (`SITE_CITATION`, per-table catalog entries' `source`/`license`/`as_of`) rather than inventing new citation formatting — one line per table referenced in the query's `FROM`/`JOIN` list, plus the site citation, plus the query text itself as a comment line (so the CSV is self-documenting about how it was produced, matching the scenario CSV's existing pattern of citing every input it read).

**URL-shareable queries**: base64url- or `encodeURIComponent`-encode the SQL text into a `?q=` param (`/query?q=...`), following the project's existing debounced-`history.replaceState` convention (`src/lib/url-state/`, CLAUDE.md: "never `router.replace`") rather than a Next navigation on every keystroke — same mechanism `useUrlState` already provides for the map, reused for a single query param on this route.

**Error surfacing**: `query()` already throws on invalid SQL/missing table; the console should catch and render inline (not the app's global error boundary — a bad query is expected user input, not an app failure) with DuckDB's own error message, since it's normally specific and actionable (unknown column, syntax error position, etc.).

**a11y**: a code editor control (even a plain `<textarea>`) plus a results `<table>` needs the same bar as the rest of the app — `tests/e2e/a11y.spec.ts` runs axe on `/`, `/methodology`, `/data` today and would need `/query` added to that list; a plain-text SQL `<textarea>` with a visible label and a results `<table>` with proper `<th scope="col">` headers clears axe's serious/critical bar without needing a full code-editor widget (Monaco/CodeMirror) — recommend starting with a `<textarea>`, since a rich editor pulls in real bundle weight for a feature explicitly niche (researcher tooling), and add syntax highlighting only if usage shows it's needed.

**Bundle-size impact**: zero on `/`, by construction (lazy-loaded, `network.spec.ts`-guarded). On `/query` itself: the ~7 MB DuckDB WASM + worker + parquet extension, already built and self-hosted by `scripts/copy-duckdb.mjs` — no new download infrastructure, just a new consumer of files that already exist in `public/duckdb/`.

**Privacy-policy impact**: none, if the extension-repository fallback is closed off. Verified in `bootstrap.ts`: `configureSelfHostedExtensions()` only sets `custom_extension_repository` to the self-hosted path (`extensionRepository(window.location.origin)`) **when the running core version matches `DUCKDB_CORE_VERSION`**; on a mismatch it `console.warn`s and *returns without setting anything*, which leaves DuckDB-WASM's **built-in default** (`extensions.duckdb.org`) in place — i.e., a version-pin drift silently reopens a real third-party request path (`tests/e2e/network.spec.ts` explicitly bans `extensions.duckdb.org`, but that spec only visits `/`, never `/query` — the query console shipping means this banned-host guard needs to also run against `/query`, or the mismatch fallback becomes a live privacy-policy-relevant regression the instant someone bumps `@duckdb/duckdb-wasm` without re-pinning both `DUCKDB_CORE_VERSION` constants and the extension sha256s). Recommend: extend `network.spec.ts` (or a new `/query`-specific network spec) to also assert no `extensions.duckdb.org` request when `/query` loads, closing this gap before shipping the console — right now nothing catches it because nothing visits `/query` in CI.

### Files to create / change

- `src/app/query/page.tsx` — route shell (server component wrapper).
- `src/components/query/QueryConsole.tsx` — the client component, `next/dynamic(..., {ssr:false})`-loaded, owns the `<textarea>`, run button, results grid, CSV/download button.
- `src/lib/duckdb/tables.ts` (new) — generated-from-catalog table registry: logical name → parquet path → `downloadable` (built by `build_catalog.py`, same pattern as `citations.generated.json`).
- `src/lib/export/query-csv.ts` (new, thin) — wraps `toCsv()` + citation-header assembly for a query result, parallel to `scenario.ts`'s existing wrapper.
- `src/lib/url-state/` — extend with a `q` param encode/decode for `/query` (or a small sibling module if keeping the map's URL state module free of query-console concerns).
- `tests/e2e/query.spec.ts` (new) — page loads, a canned query runs, result renders, CSV export enabled/disabled per table, and the "no `extensions.duckdb.org`" network guard for this route specifically.
- `tests/e2e/a11y.spec.ts` — add `/query` to the axe-scanned route list.
- `tests/unit/` — unit tests for the static-SQL-table-extraction used to gate CSV export (parsing `FROM`/`JOIN` table names is the one bit of genuinely fiddly logic here).
- `scripts/transform/build_catalog.py` — emit the new `tables.ts`-feeding generated file (or extend `citations.generated.json`'s sibling generation step).
- `docs/researchers/` — a short "Query console" page or section, seeding the example-query list.

**Effort estimate**: 3–5 focused days for a v1 (textarea SQL input, result grid, CSV export gated by the table rule above, URL-shareable queries, a11y pass, the two new e2e specs) — most of the plumbing (`query()`, file registration, self-hosted bundles, CSV/citation formatting) already exists and works; the actual new surface is the page, the table-name allowlist generator, the static-SQL-parse for export gating, and closing the `extensions.duckdb.org` fallback gap in a `/query`-scoped test.

## Verdicts

**Part A — PMTiles for pipelines: not worth doing now.** The real cold-load cost today is ~1.25 MB brotli-compressed (measured: 8.11 MB raw → 1.87 MB gzip -9 → 1.25 MB brotli -q11), served with `?v=` immutable caching, so it is paid once per browser per data version, not on every load. A PMTiles migration would (a) most likely not beat that number at the app's actual default world view, since a linear/network layer's low-zoom tiles need most of the geometry anyway; (b) force a choice between a technically-worse deck.gl `MVTLayer` subclass or a technically-better native MapLibre line-layer that breaks the project's one-canvas / one-data-path / single-symbology-module invariants for exactly this one layer; (c) introduce real tile-boundary seam risk on 1.25px hairlines and a testability regression (no single "data loaded" boolean, unlike every other layer's `useAsync`); and (d) needs a real fix for a byte-identical-rebuild property that fails today in a 5-minute test of the one concretely-good build route found (GDAL's PMTiles writer via `pyogrio`, pip-installable, no brew/tippecanoe/Docker needed — a genuinely useful finding if this is ever revisited, but not sufficient on its own). Revisit only if total geometry grows materially (coal, AIS) or a genuine region-zoom product need emerges.

**Part B — Query console at `/query`: worth doing, moderate effort.** `src/lib/duckdb/` is not rotted — it still builds, still has 24 passing unit tests, and its self-hosted-bundle / sha256-pinned-extension infrastructure is untouched since Phase 10. The console is additive and low-risk: lazy-load it so `/` stays untouched (`network.spec.ts` already proves the guard works), reuse the existing `toCsv()`/citation machinery unchanged, and gate CSV export by a static per-query "every referenced table must be `downloadable: true`" rule that extends — rather than reinvents — the project's existing view-only/downloadable distinction. The one real gap to close before shipping: the DuckDB-core-version-mismatch fallback in `bootstrap.ts` silently re-enables `extensions.duckdb.org`, and nothing currently tests that path because nothing visits `/query`; add that guard alongside the console. Estimated 3–5 days for a v1.
